# P9.1 — Offline Activity Journal PDF Export

## Architecture

The Activities screen owns a separate `JournalExportViewModel` and `JournalExportDialog`. History → Export DTR remains independent. No Room version/schema changes, attendance calculations, activity updates, original-photo writes, permissions, or cloud dependencies were added.

`OjtDao.journalActivities(start, end)` restricts records by inclusive stored activity date. `OjtRepository.journalReport` reads the profile and entries in one Room transaction. `JournalReport` sorts a saved-data snapshot chronologically; it preserves complete titles, descriptions, photo order, and optional saved time. Blank student names display “Not provided” with a preview warning. It never invents descriptions or queries attendance photos. A legacy attendance image can appear only if its path is explicitly attached to a journal entry.

`JournalExportService` probes photographs, renders on Dispatchers.IO, and delegates saving/sharing to the existing P9 transport. `ReportFiles` owns unique `.part` files, syncs writes, atomically renames completed PDFs, and removes only its own failed generation. DTR sharing has optional label/display-filename parameters with unchanged DTR defaults. FileProvider's existing exports cache root is reused.

## Workflow

1. Activities → Export Journal (existing outlined EXPORT symbol).
2. Choose monthly export (month/year) or custom range (typed ISO dates or calendar pickers).
3. Preview period: student, inclusive dates, activity count, attached-photo count, unavailable-photo count and up to five detailed warnings. Empty periods show guidance and disable generation. Dates must be valid, ordered, and within 1800–2400.
4. Generate PDF from the preview snapshot. New records require another preview. Generation checks photos again, so files removed since preview get placeholders and updated warnings.
5. Share PDF opens Android Sharesheet using a granted `content://` FileProvider URI. Save PDF uses local-only SAF CreateDocument with an explicit PDF MIME type.

Suggested filenames: `OJT_Journal_2026-10.pdf` or `OJT_Journal_2026-10-01_to_2026-10-15.pdf`. FileProvider advertises the same journal filename when sharing; internal cache filenames are unique UUIDs.

SAF success requires reading the destination back and comparing its byte count and SHA-256 digest. An unwritable/unverifiable provider reports failure while retaining the generated PDF for retry. Picker cancellation leaves original data untouched. Cancellation during a provider write can leave a partial user-chosen document; the app explains this and never deletes that destination automatically.

The ViewModel sets busy state before launching work, ignores duplicate requests, disables period changes during operations, and preserves pending save state across configuration changes. Process death requires a fresh preview/export. Cancel operation cooperatively cancels preview, rendering, or saving; cancellation inside native image decoding/PDF serialization takes effect when that call returns.

## PDF layout

- A4, 595 × 842 points, 36-point side margins; white background and dark text.
- Repeated MY OJT COMPANION / OJT ACTIVITY JOURNAL header, subtle maroon branding, thin gold separator.
- First-page student name, reporting period, totals; footer reporting dates and page number on every page.
- Activity date, optional time (Asia/Manila), title, and full saved description.
- Android StaticLayout wraps text; measured line slices flow across pages without dropping text. Page cursor reserves heading space plus initial content.
- One photo: centered 440 × 240-point maximum box. Two through five photos: 253 × 160-point boxes in two columns, with odd final photos centered. Rows move intact to the next page and captions identify the photo number and activity date.
- Image aspect ratios are fitted, never stretched or cropped. Unavailable images get numbered placeholders. No decorative full-page background.

## Photo handling and memory

Original paths resolve through ActivityPhotoStore's canonical private-storage check. Preview sequentially decodes small 128-pixel copies, detecting missing/unreadable files. Generation uses the existing EXIF-aware decoder, including rotations and reflections. One photograph is decoded at a time; output edges are bounded to 1200 pixels (single image) or 800 pixels (grid). Power-of-two sampled intermediate bitmaps can reach up to twice that edge before scaling. Orientation/scaling may briefly require more than one bitmap for the current photo. Each returned bitmap is recycled in finally; PdfDocument closes on success/failure/cancellation. Originals and thumbnails are never rewritten by export.

Only selected-period records are loaded. Text and photos are processed sequentially off the UI thread. Android PdfDocument can retain native page/image resources until serialization, so total memory still grows with report size: this is not an unlimited-memory streaming PDF writer. Cache exports remain available for sharing and are eligible for Android cache eviction; no original evidence files are used for temporary output. Repeated successful exports can accumulate cache files until Android reclaims them.

## Known limitations

- Preview is a record snapshot, not a lock on evidence; photos can become unavailable after preview and are rechecked during generation.
- Large image-heavy journals still incur PdfDocument native memory growth; split very large journals into smaller date ranges if device memory/storage is insufficient.
- Provider readback is required for verified-save success; some providers may write successfully but refuse verification.
- Cache eviction or process death requires regenerating a PDF; in-progress work does not survive process death.
- Complex-script/emoji appearance depends on Android's installed fonts. Page numbers show current page, not total pages.
- Automated fixture rendering does not replace manual real-photo, Sharesheet/SAF, theme, accessibility, and physical-print validation.
