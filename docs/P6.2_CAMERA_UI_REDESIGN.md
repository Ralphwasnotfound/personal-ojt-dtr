## Camera UI structure

A full-window dark dialog contains a safe-inset top bar, flexible live-preview area, and separate dark bottom control area. Controls remain outside system bars. The header shows Close, the attendance event or Activity photo label, and supported flash/lens controls. There are no opaque cards over the live image.

The centered shutter has an 84 dp target, white inner disc, maroon `#8B1717` ring, disabled state, accessible description, and subtle press scale. Gold `#D4A43A` highlights supporting controls against dark surfaces. Icons have consistent 24 dp artwork and 48 dp targets. A gentle photo-review fade and shutter scale use Compose animation duration scaling, including the system animator setting.

PreviewView uses compatible mode and `FILL_CENTER`: it fills available space with a centered crop, never stretches frames. Preview and capture request 4:3 output with a 1280×960 resolution preference and CameraX fallbacks. The saved JPEG may include more image at the edges than the live viewport, especially on tall screens. Review uses aspect-preserving `Fit` to show the whole saved image.

## Capture and review

1. Obtain permission once automatically per saved camera session, then bind CameraX to the screen lifecycle.
2. The shutter requires an initialized camera, resumed app, no camera error, and no ongoing operation. An immediate UI latch and the existing synchronous ViewModel gate reject repeated requests.
3. CameraX writes to the existing temporary file. Callbacks retain the session ID; ViewModels reject callbacks for another draft. Completion releases the local latch even if a failure happens before recomposition.
4. Existing image validation completes before review. The live preview unbinds when review replaces it.
5. Review shows the whole photo, Retake, and Confirm attendance / Use photo. Processing disables actions and back dismissal and displays progress.
6. Retake removes only the current temporary capture and returns to preview. Its failure returns to an actionable error state. Closing before confirmation cancels the existing draft workflow.

## Attendance integration and timestamps

The four existing event labels remain unchanged. Draft creation now calls `DailyAttendance.validate` with current stored events, legacy sessions, and recovery actions before opening the camera. This reuses existing ordering, open-session, clock, and recovery rules. Confirmation repeats authoritative validation inside the existing exclusive recorder transaction. Capture itself never inserts attendance.

`confirmCapture` sets its busy flag synchronously before starting work. `AttendanceRecorder.confirm`, `PhotoConfirmation`, repository validation, and database constraints retain their replay protection and file rollback rules. A failed confirmation can retry; retaking cannot create a record.

Two existing times remain distinct:

- `capturedAt`: assigned by the existing recorder after CameraX saves and the image is validated. Review displays this actual stored capture timestamp in Asia/Manila.
- `occurredAt`: the current device time when the user confirms. This remains the recorded attendance time and the time printed by `AttendanceTimestamp.lines` on evidence, preserving the established workflow.

The screen explicitly explains that confirmation records the current device time and device time is not independently verified. No screen clock substitutes for metadata. The evidence JPEG still has its event label, date, and Philippine time **burned into the pixels** before database insertion. The panel now uses compact white text, consistent padding, a rounded translucent black background, and an inset near the image bottom. The original JPEG is preserved separately. Existing history viewing, original/timestamped selection, sharing, recovery, and backups remain intact.

## Activity Journal integration

The same camera and review presentation wraps `captureStarted`, `captured`, `retake`, `usePhoto`, and `cancelCamera`. Use photo appends the accepted pending attachment to the existing editor; saving the activity performs the existing durable promotion. Capturing or reviewing never saves a journal entry.

The five-photo maximum, Android Photo Picker, ordering, removal, full photo viewer, editing, and save/revision validation are unchanged. Review explains that the activity must be saved to keep the photo. Cancel and retake operate on the pending file only.

## Lens and flash support

CameraProvider checks front/back availability. Switching appears only when both selectors exist; back is preferred initially and a single available front lens is a graceful fallback. The original workflow imposed no fixed-lens requirement. Switching is disabled during capture, resets flash to Off, and rebinds only this screen's use cases. No global `unbindAll` is used.

Flash appears only when the bound camera reports `hasFlashUnit()`. The icon cycles Off → On → Auto using existing ImageCapture flash modes. These are still-photo flash modes, not a continuous torch or simulated front screen flash. CameraX handles auto exposure/flash decisions; actual vendor hardware behavior needs device testing. Flash changes update ImageCapture without rebinding. A no-flash lens always receives Off.

## Permissions, errors and lifecycle

- A denied permission does not trigger repeated prompts. The screen offers app settings, which also handles permanent denial. Permission is checked on resume; users can close the camera and activity users retain the picker alternative.
- Missing lenses, provider initialization/bind failure and CameraX camera-state errors show concise recovery text and Retry camera. A 15-second initialization timeout also exposes retry/close instead of indefinite loading.
- CameraX file I/O errors ask the user to check free storage. Interrupted-camera and general capture failures unlock the workflow and permit retry/cancel. Existing processing/save errors remain visible.
- Lifecycle binding pauses camera operation in the background. The shutter is disabled while the app is not resumed. CameraX callbacks report interrupted requests; successful captures may finish processing in the background without creating attendance automatically.
- Disposal ignores late provider initialization, removes the camera-state observer, and unbinds only the owned Preview and ImageCapture. Lens/retry changes rebind; ordinary recomposition and flash changes do not.
- Rotation recreates the view/lifecycle binding as needed. Existing ViewModels retain capture/review state, lens/flash/requested-permission preferences are saveable, and display rotation is refreshed at capture. No new process-death persistence is introduced: abandoned attendance drafts use existing recovery and journal editor state uses existing SavedStateHandle/storage recovery.

## Performance

No real-time effects, new image libraries, network dependencies, or full-resolution Compose decoding. Review reuses `LocalPhoto` and the background EXIF-aware decoder capped at 1000 pixels. Evidence processing retains the existing IO dispatcher, bounded decode and JPEG pipeline. Resolution preference, 90% camera JPEG quality and minimize-latency mode remain. Preview uses no per-frame Compose state updates. Only a tiny press animation and review alpha transition are added.

## Samsung Galaxy A06 validation checklist

Use a normal update installation with the same application ID/signing key; do not uninstall or clear storage. If recording real attendance, only confirm genuine events at their actual time. Use a separate test environment for synthetic four-event/recovery cases. A user-initiated local backup can protect records before device validation.

- [ ] Open attendance capture for the allowed event; verify its label, preview crop, white controls and system-bar clearance in portrait and landscape.
- [ ] Tap shutter rapidly; verify one capture/review. Retake repeatedly and confirm no attendance record exists before Confirm attendance.
- [ ] Confirm once and rapidly tap again; verify exactly one event, original photo and stamped photo, with correct next event and unchanged hour calculation.
- [ ] Delay at review: verify the displayed capture time differs from confirmation time as expected. Inspect the saved/shareable stamped JPEG for its readable event/date/time panel and unchanged original.
- [ ] Verify all four legitimate events and unavailable events, earlier open session, legacy session and recovery/skip cases retain existing restrictions.
- [ ] Switch lenses repeatedly, then capture/review each available lens. Verify orientation, aspect ratio and absence of distortion. On single-lens hardware, switch must be hidden.
- [ ] Cycle flash Off/On/Auto on the back camera in bright/dim conditions. Verify no-flash front camera hides flash. Verify switching resets to Off.
- [ ] Journal: capture, retake, cancel and Use photo; verify text remains, capture alone saves nothing, and Use photo adds one pending attachment.
- [ ] Combine picker and camera photos up to five. Verify a sixth is blocked; reorder/remove/view, save and reopen an edited activity.
- [ ] Deny permission, reopen/rotate, and verify no repeated automatic prompt. Grant in settings and return; revoke in settings and verify safe recovery.
- [ ] Test camera contention with another app, initialization retry and interruption during capture. Verify useful errors and working retry/cancel.
- [ ] Background/resume and rotate during preview, capture, review and confirmation. Verify no stuck progress, duplicate record or lost editor text.
- [ ] On a test device with limited free storage, exercise capture and confirm failure, then free storage and retry. Verify existing evidence/records remain intact.
- [ ] Verify TalkBack names, disabled controls, large fonts, gesture/three-button navigation and animator scale disabled. Confirm Retake/Use photo remain reachable.
- [ ] Observe repeated capture/retake/switch sessions on the A06 for responsiveness, memory pressure and preview cleanup when closing.
