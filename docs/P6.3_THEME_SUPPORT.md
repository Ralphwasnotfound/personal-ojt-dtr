# P6.3 — Complete light/dark theme support

## Theme selection

Profile & settings → Appearance → Theme opens a Material 3 radio selection dialog:

- **System Default** (new-install default): resolves against the current device light/dark configuration.
- **Light**: always uses the light BSIT palette.
- **Dark**: always uses the dark BSIT palette.

The row displays the saved choice. Selecting an option saves it asynchronously and updates the existing Compose theme immediately after the write succeeds. No restart, profile Save settings action, activity recreation, navigation reset, or attendance/database operation is required. A brief saving indicator prevents overlapping writes. Read/write failures show a concise error; failed writes retain the prior selection and can be retried.

The radio group has one accessible selection target per row, a minimum 56 dp row height, and the current option selected. Cancel leaves the saved setting unchanged. Profile field drafts retain their existing rememberSaveable state during theme changes.

## Persistence and startup

`ThemePreferences` uses Preferences DataStore in the app-private `files/datastore/appearance.preferences_pb` file, key `theme_mode`, stable string values `system`, `light`, `dark`. The Application owns access to the singleton Context delegate. The activity's `ThemeSettingsViewModel` observes it through StateFlow and saves choices in its own lifecycle scope.

There was no pre-existing app appearance preference or general settings store in the inspected source. Glance already brings in DataStore 1.0.0; this phase explicitly declares that same version for direct application use. It adds no second storage framework and does not access Glance's widget-state files. Room's profile, attendance and activity entities are unchanged.

Missing values resolve to System Default without writing a default over disk. Existing explicit light/dark values are honored, and unknown future string values fall back to System Default without being overwritten merely by reading. No corruption reset handler or destructive migration is introduced. A read failure falls back to a usable System Default UI with an Appearance error; selecting a theme retries storage access.

Preferences survive app/process restarts, device restarts and normal app updates because they are stored in app-private persistent storage. This does not imply survival after uninstall or clearing data. Neither action was performed.

The app waits for the initial preference result before composing navigation, avoiding rendering an incorrect app theme and then replacing the navigation tree. Android's launch/splash/window resources follow the **device** configuration before the asynchronous app preference is available; an explicit opposite preference may therefore differ from the brief OS launch surface. Day/night window backgrounds prevent the old unconditional white launch window on a dark device.

Appearance is a local app preference and is intentionally **outside the existing manual backup format**. Export/restore retains its existing data compatibility and does not replace the current appearance preference. Profile's backup explanation and restore preview now state this distinction.

## Camera behavior

The P6.2 live-preview shell stays dark, with white header icons, white shutter, maroon shutter ring and gold accent. Its small palette is now centralized. Changing the app theme only recomposes color providers; `CameraPreview` binding keys, CameraX controls, callbacks, timestamps and draft/confirmation logic are unchanged.

Photo review's header, supporting surface, text, processing indicator and Retake/Confirm buttons use the selected app theme. The captured image itself retains a black viewing area with readable white fallback text. Permission explanations/settings controls use the selected theme. Camera errors use the selected app error-container/on-error-container pair even while live preview remains dark. Review/permission system-bar icons follow the app theme; live preview uses light system-bar icons.

No theme transition creates an attendance event, attaches a photo, resets a camera session, changes the five-photo limit, deletes evidence or rewrites an image. Existing shutter/review fades continue following system animation duration scaling.

## System UI and configuration changes

MainActivity uses AndroidX `enableEdgeToEdge`/`SystemBarStyle` with detection based on the **resolved app theme**, so a Light selection on a dark device still requests dark status/navigation icons and vice versa. AndroidX provides the platform-appropriate transparency/scrim handling.

Dialogs own separate windows. `DialogSystemBars` applies the same icon appearance to their WindowInsetsController. Full-window photo/editor/camera dialogs also use AndroidX `WindowCompat.enableEdgeToEdge`, transparent system bars and their existing safeDrawing/IME padding, with content surfaces drawn behind the inset areas. Alert and picker dialogs retain their normal layout and selected-theme content.

MainActivity handles `uiMode` configuration changes itself. Compose's system configuration still updates, so System Default responds to device changes without recreation for theme alone. Explicit Light/Dark choices remain fixed. No AppCompat global night-mode recreation is used. Rotation keeps its existing lifecycle/recreation behavior; this phase changes no CameraX lifecycle policy.

Theme changes are direct, lightweight recoloring. No full-tree Crossfade, navigation key changes or heavy effects are used. This avoids maintaining two camera/navigation trees during a transition.

## Widget behavior

The P5.1 widget continues to follow the **device system theme**, independently of the in-app selection. Its ColorProvider resource references and `values/widget.xml` / `values-night/widget.xml` definitions are unchanged. It is not redesigned, and no theme-preference observation or additional refresh is added to the widget. Existing launcher/Glance refresh, boot/update handling, repository observation and shortcuts remain unchanged.

For example, selecting Light in the app while Android is Dark intentionally yields a light app and dark widget. Switching Android itself changes the resource variant used by the launcher/widget through its existing lifecycle. OEM refresh timing still requires device verification.

- [ ] Restart the app and reboot the phone. Verify the selected choice remains. Verify a normal update preserves it too.

- [ ] In both themes visit Dashboard, Attendance, Activities, History and Profile. Inspect empty, loading and error states, text contrast, fields, navigation and snackbar actions.
- [ ] Open activity detail/editor, date/time picker, discard/delete/error dialogs and photo viewer. Check selected/disabled states, large fonts, TalkBack radio selection and keyboard/IME clearance.
- [ ] Open attendance and activity camera in each app theme. Verify live preview remains dark/white-controls; permission explanation, errors and review supporting surfaces use the chosen theme.
- [ ] Change device dark mode during live capture/review with System Default selected. Verify no theme-only activity restart/rebinding, lost draft or duplicate attendance. Check rotation separately using the P6.2 checklist.
- [ ] Capture, retake and confirm genuine attendance; verify confirmation-only saving, timestamps, evidence sharing and unchanged calculations. Confirm activity Use photo still adds only a pending attachment and the five-photo limit remains.

## Known limitations

The OS launch surface and external Android/OEM sheets follow device configuration; in-app explicit selection applies after the asynchronous preference read. The widget intentionally follows device theme. Appearance is local and not included in the pre-existing manual backup format. Runtime layout, system-bar behavior, actual camera continuity and Samsung launcher refresh still require the device checklist above.
