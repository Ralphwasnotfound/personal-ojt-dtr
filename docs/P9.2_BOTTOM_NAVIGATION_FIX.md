# P9.2 — Bottom navigation return-to-Home fix

## Investigation and root cause

The app has one remembered NavHostController and five flat routes: dashboard, attendance, activities, history, profile. Home is the label for dashboard. The controller is keyed only by the existing backup-restore revision, not by the selected tab. The current back-stack entry drives selection. Dashboard has no local navigation controller or touch overlay. Screen content consumes Scaffold padding above the bottom bar. Camera, export, editor, and confirmation dialogs deliberately block interaction while visible.

The initial A06 controller test passed all simple Dashboard → tab → Dashboard round trips. The cross-tab-only sequence also passed. A mixed navigation sequence failed: Dashboard's shortcut uses navigate("attendance") with only launchSingleTop; tapping Home then invokes popUpTo(start) with saveState and restoreState=true. The controller's saved-stack mapping can associate the just-popped shortcut stack with the Dashboard start destination. Restoring that mapping reopens Attendance instead of leaving Dashboard on top. Baseline device assertion: `Shortcut attendance then dashboard expected:<dashboard> but was:<attendance>`.

A separate real-pointer test against the unfixed installed app also failed after opening Dashboard’s Profile shortcut and tapping Home. The same shortcut-return test passed after installing the fix.

This explains the intermittent nature: the entry path matters. The failure was reproduced using the app's actual Navigation Compose 2.9.5 dependency on a physical SM-A065F, not inferred from code alone. The first failing harness assertion escaped its main-thread callback and terminated instrumentation; the harness now returns failures to the test thread for normal JUnit reporting.

## Minimal implementation

`TopLevelNavigation.kt` defines one `NavController.selectTopLevel` policy:

- Ignore a tap on the active destination (including its parent graph).
- Pop up to the graph's start destination, saving the outgoing tab state.
- Use launchSingleTop to avoid duplicate entries.
- Restore saved state for other tabs, but **never restore a saved stack when selecting Dashboard**, which remains retained below the popped entries.

Bottom-tab taps, Dashboard shortcuts, History's Attendance link, and existing widget navigation now call this same policy. Widget intent consumption and Activities detail selection remain unchanged. Selection uses destination hierarchy so a nested child can highlight its parent correctly.

The existing NavHost, five routes, remembered controller, restore-revision behavior, composables, tab sizing/colors/icons, and screen state ownership remain intact. No database, records/photos, attendance, camera, exports, backup, theme preferences, widget destinations, or branding changes.

Back from a top-level tab returns to Dashboard rather than walking the tab switching history. Active-tab taps preserve the current entry. Existing dialogs retain their own Back/dismiss behavior. Saved tab state and controller/activity recreation are tested.

## Regression tests

`BottomNavigationTest` uses a real NavHostController and ComposeNavigator on the device, with isolated graphs and ViewModelStore. It covers each tab's Home round trip, repeated cross-tab cycles, legacy shortcut stacks, rapid switching and repeated active taps with entry counts/identity, Back, saved tab state/controller restoration, and a synthetic nested graph's restore/Back behavior. It does not touch Room or user data.

`BottomNavigationTouchTest` launches the installed app and injects real pointer events into bottom-tab icon/label areas through UiAutomation. It verifies enabled/selected semantics, only one selected tab, minimum 48dp item width/height, actual Dashboard content, all tab round trips, cross-tab switching, a Dashboard shortcut, repeated taps/Back, a read-only journal-export dialog, and Activity.recreate(). A test-only composition switches between explicit Light/Dark themes and verifies that the selected tab survives recomposition and Home remains tappable; it never writes the stored theme preference. No preference/record edits are performed.

## Samsung A06 manual checklist

1. In both Light and Dark modes, tap Home's icon and label after each other tab. Confirm Dashboard content and Home highlighting agree.
2. Run Dashboard → Attendance → Activities → History → Profile → Dashboard in both directions, then repeat rapidly.
3. From Dashboard, open the profile shortcut, attendance Open shortcut, and activities View all/recent-activity shortcut. Dismiss any detail dialog, then tap Home.
4. Tap an active tab repeatedly. Press Back from a different tab: expect Dashboard, not repeated copies of the tab. Back on Dashboard follows normal Android app-exit behavior.
5. Open and dismiss Export Journal and Export DTR; return Home. Open/close a journal detail without editing it. Verify the underlying tab remains selected.
6. Rotate/recreate on Profile or Activities, then switch Home and back. Verify retained screen state and no duplicate destinations.
7. After any deliberate modal operation, dismiss/finish it before testing the bottom bar; dialogs intentionally intercept touches.

## Scope and limitations

Automated controller restoration is not a full OS process-death test. Camera capture, destructive restore, and editing/saving real records are intentionally excluded from navigation tests. The Light/Dark test overrides only its composition; it does not modify the user's theme preference. Existing data-operation busy states still intentionally disable all tabs until the operation completes.
